# 个人记录 RAG 业务建议

日期：2026-11-19。本文补充 [AI 事件录入方案](ai-event-entry-design.md)。全文日记 RAG 已完成本地实现；向量和混合检索仍为后续设计。尚未发布服务器，实施说明见 [AI 与日记问答](ai-rag-implementation.md)。

## 1. 先做“问问我的记录”

首个 RAG 业务选择日记问答：用户用自然语言查找、归纳本人已经保存的记录，回答附日期、原文片段和可打开的日记入口。

示例问题：

- 我最近记录过哪些跑步后的感受？
- 上次去杭州，我写了哪些值得注意的事？
- 关于项目上线，我之前记过什么问题？

回答应明确区分“原文记录的事实”和“AI 建议”。没有找到足够材料时提示未找到相关记录，不能编造过去发生的事。检索是有范围和召回限制的，因此“没找到”不代表用户从未记录过。

默认只查询本人日记。后续扩展到本人计划、时间线和用户主动选择的笔记；收到的分享计划不会自动扩大为对方日记或整个账号的访问权。

## 2. 业务扩展次序

| 阶段 | 功能 | 实现重点 |
| --- | --- | --- |
| R1 | 日记检索问答与来源定位 | 检索、上下文拼装、生成、引用校验 |
| R2 | 中文语义检索与全文混合检索 | Embedding、分块、向量索引、召回融合 |
| R3 | 参考历史辅助录入或预排 | 检索相似经历，生成建议，用户确认 |
| R4 | 有明确范围的周/月回顾 | 全量范围读取、确定性统计、分批摘要 |
| 可选 | 用户主动建立的个人知识笔记 | 笔记管理与删除，作为独立可授权数据源 |

与 AI 录入的区别：事件录入主要把当前这句话转换为草稿；RAG 问答还会先检索历史资料，再让模型依据资料回答。

## 3. 第一阶段复用现有 ES 全文检索

RAG 可以基于全文检索实现。第一期先复用已有中文日记索引，建立“检索 → 校验 → 提供上下文 → 生成带来源答案”的完整闭环，无需新增向量数据库或独立 AI JVM。

现有日记搜索具备：按 accountId 限定、过滤 deleted、日期范围查询、按命中日期从 MySQL 回读，并校验当前版本。应复用这些安全规则，而不是直接把 ES 返回的旧正文发给模型。

不能直接把完整自然语言问题交给现有 `operator=and` 的关键词查询就认为召回足够。新增专用检索逻辑，抽取关键词和日期范围、设置合理的匹配规则，限制候选数量，并测量中文问题的召回表现。可先使用规则处理日期，再视样本需要增加有预算限制的查询改写。

建议先取 10～20 条候选，经过 MySQL 版本和权限回查、片段截取与去重后，只发送最相关的 3～5 个片段，并设置总上下文 token 上限。第一阶段一次最多一条回答生成请求；如增加模型改写，必须将额外请求纳入用量和延迟预算。

第一期可提出的链路：

```text
问题与日期范围
    ↓
服务端绑定当前账号
    ↓
检索 ES 相关日记
    ↓
MySQL 回查账号、删除状态和当前版本
    ↓
选择片段，生成服务端来源编号
    ↓
Spring AI + DeepSeek 根据材料回答
    ↓
校验引用编号，返回答案与原文入口
```

Spring AI 2.0 提供模块化 RAG 的 `RetrievalAugmentationAdvisor`，可通过自定义 `DocumentRetriever` 接入自己的检索器；也可以先把流程放在清晰的业务 Service 中显式编排。[官方 RAG 文档](https://docs.spring.io/spring-ai/reference/api/retrieval-augmented-generation.html)

## 4. 第二阶段加入向量与混合检索

全文检索对精确名称、关键词有用；语义检索用于查找措辞不同但主题相近的内容。结合两路候选并做融合排序，再按来源与片段去重。

使用 Spring AI `EmbeddingModel` 和 `ElasticsearchVectorStore`，在现有 ES 进程中建立独立的版本化向量索引，先核对当前 ES 版本、客户端版本和内存支持情况。不能让 VectorStore 自动初始化覆盖当前日记全文索引。[Spring AI Elasticsearch 文档](https://docs.spring.io/spring-ai/reference/api/vectordbs/elasticsearch.html)

DeepSeek 用于最终回答；Embedding 模型单独选型。现有 DeepSeek API Key 不能据此视为已经具备文本向量服务。选型时核对中文效果、单次长度、向量维度、远程调用费用和供应商的数据处理要求。当前 2GB 服务器先考虑远程 Embedding，不能直接承诺再部署本地模型有足够内存。

分块建议从自然段开始，按所选模型的 token 限额设置块长与少量重叠；短计划通常一条一块。每块保存：

`accountId`、`sourceType`、`sourceId`、`sourceRevision`、`date`、`chunkId`、`chunkIndex`、`embeddingModel`、`embeddingVersion`、`chunkerVersion`。

相同模型和版本分别用于文档与查询；更换模型或维度时重建新索引并切换别名，不混用旧向量。

向量更新使用独立的 `rag_index_jobs` / outbox，记录来源与版本。现有日记 outbox 被全文索引消费者成功处理后会删除，不能直接增加一个消费者竞争同一批任务而假设两种索引都会更新。Node 和 Java 两条写入路径都要触发任务，或建立有检查点的增量对账，避免正式端写入后 RAG 长期不更新。

先生成完整的新版本块，再启用新版本并清理旧块；检索仍要回查当前源记录。删除和权限变化立即使检索及答案缓存失效，后台清理向量不能成为继续回答已删除材料的理由。

## 5. 三层结构与跨服务调用

建议 AI 编排继续放在原方案的 calendar-service，复用拟定的 ChatClient 配置、身份桥接、用量限制和审计，避免再建独立进程。

建议接口：`POST /api/ai/knowledge/ask`。请求只允许问题、日期范围和可选的数据源；accountId 来自鉴权上下文。

建议分工：

- `KnowledgeController`：接收问题、输出结构化答案。
- `KnowledgeService`：检索、片段处理、模型调用与引用校验。
- `DiaryKnowledgeClient`：调用 diary-service 内部检索能力。
- diary-service 的 `DiaryRetrievalService`：执行账号与版本校验、组织命中片段。
- `DiarySearchDao` / `DiaryEntryDao`：访问 ES 和 MySQL。
- `KnowledgeAnswerResponse`、`EvidenceSnippet`：明确的业务 DTO。

服务间必须传递服务端验证过的短期身份上下文，账号约束在检索服务中再次强制执行，不让模型或前端覆盖过滤条件。正式 Node 入口沿用 AI 方案中的受控身份桥接，不能直接转用 Cloud token。

回答响应包含 answer、sources、coverage、warnings。每个 source 包含内部编号、日期、日记标识、版本与摘录；原文链接由程序构建，模型只能引用已给出的编号。引用存在不代表内容必然被支持，评估时还需检查每个关键结论与证据是否一致。

## 6. 不能用 Top-K 搜索代替完整统计

“我这个月完成了多少计划？”应读取当前账号指定月份的完整数据，由程序计算，再由 AI 解释结果。

“总结上个月全部日记”需要覆盖整个月，超过上下文时分批处理并记录覆盖情况。不能只查五条最相关日记后声称总结了全部记录。

“最近关于跑步的记录有哪些？”适合相关性检索。响应应标明当前日期范围和是否只展示部分相关材料。

## 7. 隐私、成本与质量

- 用户主动使用历史问答时，明确说明会把必要的本人历史片段发送到 DeepSeek；原事件录入默认仍只使用当前输入，不自动读取日记。
- 文档内容作为不可信资料处理；其中的指令不能覆盖系统规则，也不能触发工具写入。
- ES、向量检索、MySQL 回查和缓存均绑定账号；缓存键还要包含问题、范围、模型/提示版本与数据版本。
- 数据更新、删除后不复用旧答案缓存；每次发送模型前核对资料版本，打开原文时再次鉴权。
- 无资料或检索服务不可用时不生成带有虚构个人经历的答案，可回退到原关键词搜索页面。
- 用量限制包括查询改写、Embedding、回答生成等所有外部模型调用；Embedding 的历史回填应可暂停、重试和限速。
- 第一版最多一个并发回答请求，避免与日记索引争用线程池；具体上下文和输出上限通过样本测试确定。

评估样本至少覆盖：能回答、没有相关记录、同义表达、日期范围、删除与修改、两个账号内容相似、资料中的提示注入、错误引用和统计问题。分别检查召回是否找到正确材料，以及答案是否忠实于材料。

## 8. 推荐实施顺序

先完成 Boot 4 + Spring AI 2.0 的基础升级及事件草稿录入，再交付“日记问答＋原文来源”的全文 RAG。用真实使用样本评估之后，增加远程 Embedding 和 ES 混合检索，最后接入参考历史的时间预排。

这样每一步都有可使用的业务结果，也能逐步学习检索、生成、向量、索引一致性和 RAG 评估。
